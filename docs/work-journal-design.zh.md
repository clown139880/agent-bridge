# 工作日志：每天把 agent 干了什么写进笔记

状态：Control Plane 部分已实现（0.7.90，`apps/control-plane/src/journal.ts`），原型已用 2026-11-09 至 11-11 的真实数据跑过四版（§10）。本阶段：整理昨天的对话 → 进度写进日记，记忆直接归档进中央记忆。早上简报放到下一阶段。

## 1. 要解决的问题

项目多、agent 多，旧任务在续、新任务在开。隔一天人就说不清：

- 昨天哪些事做完了，哪些还没做完；
- 哪些在等我（审批、提问，或者 agent 最后一句在问我）；
- 哪些被重启、部署打断了，之后没人接着做——我以为它跑完了，其实没有；
- 没有推送的自动任务到底跑没跑。

笔记里的 LifeOS（项目卡、每日笔记、任务）本来就是管这件事的，只是人已经不手写了。所以由系统每天替人写：把 agent 的工作整理成项目进度和待办，写进每日笔记。

同一遍整理顺带产出「记忆候选」（见 §7），作为自我进化的入口：由归档步骤直接写入中央记忆（默认写项目作用域），不进笔记；归档拿不准的放进 Control Center 的记忆审核队列，由人一条条处理。

## 2. 总体结构

```
Control Plane（通用，开源）                      agent-skills（个人）
┌──────────────────────────────────────┐        ┌──────────────────────────────┐
│ journal 模块                          │        │ automations/daily-journal    │
│  ① 按游标收集变化：会话、turn、请求、  │  API   │  每天 07:00                   │
│    automation 运行                     │◀──────│  ① POST /journal/runs 生成     │
│  ② 程序判状态（不经 LLM）              │        │  ② 读笔记里的勾选 → 回写 CP    │
│  ③ LLM 写进度摘要、判断是否在等人、    │──────▶│  ③ 渲染 LifeOS 段落写进日记    │
│    归档记忆候选                        │        │  ④ 按归档结果写入中央记忆      │
│  ④ 条目账本（跨天，未关闭的一直挂着）  │        │  （⑤ 简报：下一阶段）          │
└──────────────────────────────────────┘        └──────────────────────────────┘
```

- **Control Plane 的 `journal` 模块**：只做通用的事——从自己的数据库算出「这段时间每个会话、每个自动任务发生了什么、现在处于什么状态」，维护跨天的条目账本，对外给 API 和 MCP 工具。不做开局注入：要不要接着做由人决定，作用域记忆本来就会注入。不知道 Obsidian、LifeOS、哪个房间。
- **agent-skills 的 `daily-journal` 自动任务**：个人的部分——作用域到 LifeOS 项目 tag 的对照、笔记路径、段落格式、简报措辞和投递房间。它是一个普通的 `script` 任务。

这样开源仓库里没有个人部署值（笔记路径、房间 ID 都在任务定义里），换一个笔记系统只需要换渲染脚本。

## 3. 状态怎么判断

每个条目归到一个会话（或一个自动任务），状态由**程序**根据数据库判断，LLM 不参与：

| 状态 | 判断依据 |
| --- | --- |
| ✅ 完成 | 区间内最后一个 turn `completed`，且 LLM 判断没有在等人、没有明确的下一步 |
| 🔄 进行中 | 会话有 `activeTurnId`，或最后一个 turn 完成但 LLM 判断还有 agent 自己要做的下一步 |
| 🙋 等你 | 有未处理的审批或提问；或最后一个 turn 完成，但 LLM 判断最后一句在问人、等人拍板 |
| ⏸ 被打断 | 最后一个 turn 是 `interrupted` / `unknown`，或 turn 还挂着而 Bridge 已重启，**且之后没有新的 turn**；人用 `!stop`/⏹ 主动停的不算 |
| ❌ 失败 | 最后一个 turn `failed` |

「在不在等人」「有没有下一步」是唯一交给 LLM 的判断，它只能把 ✅ 改成 🔄 或 🙋，不能把程序判出来的 ⏸、❌ 改掉。原型实测「等你」偏多（一天 9 条左右，包括请求删除临时文件这类确认），可以接受，不再收紧。

**哪些会话不算：** 由自动任务创建的会话（会话创建时间与某次 `automation_runs` 的开始时间相差不到 2 分钟）只进自动任务汇总。接收自动任务推送、但也有人说话的会话（例如房间会话）照常列出。别的程序经 Bridge 发起的会话（例如电台的观众对话）目前还分不出来，以后要在 turn 上记录发起方。

要分清「人主动停的」和「重启打断的」：Bridge 失去一个 turn 时（重启、换进程）记下的 `turn.interrupted` 带 `reason`（例如 `worker no longer owns this turn`），人或 agent 自己停的没有；turn 开着却没有结束事件、会话也不再运行它的，同样算被打断。interrupt 动作只保留 24 小时，第二天查不到发起方，所以不用它判断。

自动化不按会话列，只按任务汇总：区间内跑了几次、成功几次、失败几次、静默几次；**该跑没跑**（调度时间已过却没有运行记录）单独标出。有自己推送的任务只出现在汇总那一行里；没有投递目标的任务失败或该跑没跑时，才单独列一条。

## 4. 增量：只处理变化的部分

按天运行：一次处理一天（默认是昨天，按任务的时区切），同一天可以重跑。

- 当天有人或 agent 说过话、或开过 turn 的会话才算这一天的会话；事件按它自己的时间归到哪天，迟到补传的也归回原来那天。
- 每个会话已有 `view_revision`（每存一个事件、每改写一次就加一，`packages/database/src/view.ts`）。每天每个会话的摘要连同当时的 revision 存进 `journal_sessions`；重跑时 revision 没变就直接复用，只有变了的会话才再调模型。
- 归档同理：候选集合的哈希没变就复用上次的决定（`journal_archives`）。
- 摘要生成失败的不缓存，下次重跑再试。同一天同时只跑一次，后来的调用等它的结果。

## 5. LLM 写摘要

只对 revision 变了的会话调一次模型，复用 Control Plane 已有的 TokensAPI 模型客户端（`review-model.ts`，默认 `deepseek-v4-flash`，带备用模型；夜里 GQX 睡眠也不受影响）。

- **一个一个调，不并发。** 夜里跑，不赶时间；模型的并发额度和在线的审核员共用，并发会撞上限（HTTP 429）。一天约 20 个会话、7 分钟。
- **预算要给够。** 模型先思考再回答，长会话 4500 token 会在思考里耗尽（`finish_reason=length`）。摘要给 12000，每批归档给 5500；没解析出 JSON 就重试一次。

输入（有界）：会话标题、项目、程序判出的状态、区间内的用户消息和 agent 回复（不含工具输出），超长时保留开头、人的每一条消息和最后几轮。消息标明「人」还是「agent」。

输出（JSON）：

```json
{
  "title": "不超过 16 字的会话主题",
  "done": ["做成了什么，一句一件"],
  "next": "agent 自己接下来要做的事，没有就空",
  "waitingOnHuman": "要人做的决定或动作，没有就空",
  "memory": [{ "kind": "preference", "value": "…", "evidence": "MM-DD HH:MM「人的原话」" }]
}
```

提示词里的规则（原型迭代出来的）：

- `done` 只写 1 条，50 字以内：一个会话就是一件事，方案、实现、测试、上线合成一句，写它最后到了哪一步（模型给了几条也合成一行）。只写结果（上线了什么、查明了什么、定了什么），不写过程（「澄清了意图」「保存了文件」）；只留一个关键数字或版本号，不写 PID、提交哈希、IP、路径、测试条数。
- `waitingOnHuman` 只在 agent 明确停下来等人拍板、给信息或做它做不了的动作时写；结尾的客套（「需要的话告诉我」「请验收」）不算。
- `memory` 见 §7。

失败时退回程序的判断，只写「有进展，摘要生成失败」，不影响状态列表。

## 6. 条目账本

条目是跨天的：一件事没关闭，就一直挂着，直到被关闭。

- 表 `journal_items`：`id`（稳定：会话条目 `jn-<会话 ID 前 8 位>-<MMDD>-<种类>`，自动任务 `jn-a-<任务 ID>-<MMDD>`）、`date`（写在哪天的笔记里）、`kind`（`next` 下一步、`human` 等你、`interrupted` 被打断、`failed` 失败、`automation` 自动任务失败或该跑没跑）、`title`、`scope`、`session_id`/`automation_id`、`opened_at`、`closed_at`、`closed_by`（`human` / `auto`）。
- **自动关闭**：会话在条目那天之后又开了 turn（续上了、重试了、人回应了），或者自动任务之后跑成功了——下一次运行时由程序关闭（`closed_by=auto`）。记忆不进账本（§7），旧版本留下的记忆条目在下一次运行时删掉。
- **人关闭**：人在笔记里勾掉这一条（见 §8），脚本把它回写给 CP（`closed_by=human`）。
- 重跑某天时，那天还没关、这次不再产出的条目删掉；已关的不再打开。

同一件事一个 ID，所以重跑、重新生成都不会出现两条。

## 7. 记忆候选（自我进化的入口）

分两步：每个会话的摘要顺带提出候选，所有会话处理完后再调模型做归档。归档结果直接写入中央记忆，`derived_from` 指回原消息；不进笔记。

**提候选（摘要那一步）：**

- 只认人本人说的话：消息来源要能确认是人（从 Matrix/客户端进来的人类输入），跨会话转来的消息、自动任务的 prompt、agent 的转述、日报和简报本身都排除。来源确认不了就不提。
- 只提「以后干活怎么做」：人纠正了 agent 的做法，不记下来以后的 agent 还会犯。
- 不提「要做什么」：功能需求、产品设计、架构选择、模块怎么拆、放哪个仓库、复用哪个账号、配色样式文案、界面怎么摆——做完就在代码和文档里。也不提一次性的值、只对这一次有效的指令、agent 自己的总结。
- 例外：人说明的、会持续一段时间的自身处境（收支、资产用途、设备状况），以后在这个作用域回答问题要用到，记为 `fact`。
- `value` 写明适用范围：只对这个项目或工具成立的写成「在 X 里……」，不写宽成通用规则；人明确说「所有 App 都这样」才写通用形式。
- 大部分会话没有候选。

**归档（按项目分批）：** 一个项目的候选一批，每批最多 8 个，各调一次模型。忙的一天有几十个候选，一次全给，模型会在思考里耗尽预算，或给出坏掉的 JSON（11-12 有 29 个候选，两次都失败，全部转给了人）。哪一批失败，只有那一批的候选转给人；有批次失败的这一天不缓存，下次运行重新归档，成功后那些条目自动消失。每批给出每个候选所在项目的作用域及其已有记忆，再加上 `_global` 已有的记忆（全文，冲突常在长句后半），模型对每个候选决定：

- `project`（默认）：写项目作用域。会话的作用域直接取 Control Plane 写在会话上的分组（`sessions.group_key`），和记忆解析是同一套规则，journal 不自己匹配目录。
- `global`：只在人明确说是通用做法时才选，写入时再经过 `_` 作用域的自动审核。
- `skip`：要做什么、目标作用域已有同义记忆、拿不准的。即使写成「在 X 里……」，只是这件事的设计也照样 skip。
- 同一主题的几个候选合成一条；和已有记忆说法相反的照样给决定，但写明冲突的是哪条，交给人审。
- 模型漏掉的候选不悄悄丢，列为「待定」。

**交给人的：** 能照原样写入的（作用域已有、主题合法），直接放进记忆审核队列（`memory_reviews`，状态 `waiting_human`，跳过审核模型），人在 Control Center 会话页的审核面板里逐条允许或拒绝；同一条写入重跑不会重复入队，决定上带 `review` 指向它。写不成的（漏掉的、没有主题的）只计数，日记里给自动任务的链接。
- `pin` 只给几乎每次在该作用域干活都需要的。

**没有作用域就新建：** 候选要写进项目作用域，而会话所在目录还没有作用域时，由归档模型起名，用 memory 的 `scope` 工具建一个 provisional 作用域：`{ machine_id, cwd, repository?, scope_hint, title, create: true }`。

- id 用英文单词，不用拼音：目录名能看出是什么就按目录起，起不好（中文、日期、单个字母）就按内容起（例如中文目录「挂刀」→ `steam-trading`）。`title` 写这个目录整体是什么，不写当天聊的那件事。
- 只绑会话所在目录本身（有仓库就一起绑），不绑父目录。目录已有绑定时不会重复建，所以每次都可以带 `create: true`。
- 建完 Control Plane 立刻重新分组；绑错了用 `scope_bind` 改，起错名用 `scope_rename` 改。

写入前核对槽位：生成候选之后，人或别的 agent 已经改过同一个「主题 + 类别」，就放弃这个候选，在日记的自动任务行里提一句。

原型实测：同样的输入重跑，个别候选的决定会变（有时 skip，有时写入）。每晚只跑一次，结果靠写入审核兜底，可以接受。

## 8. 写进 LifeOS 每日笔记（agent-skills 部分）

**写在哪天：** 事情发生在哪天，就写进那天的日记（`0. 周期笔记/<年>/Daily/<月>/<日期>.md`）。日记不存在就按 `0. 周期笔记/Templates/Daily.md` 建一个。

**写在哪里：** 不另开标题，放在 `## 日常记录` 末尾（人手写的内容之后、`## 习惯打卡` 之前），用标记围起来，按项目分组：

```markdown
%%agent-journal:start — 本段由 agent 维护，重新生成时整段替换（勾选状态按链接里的条目保留）%%
- Agent Bridge
	- [x] 房间绑定 hal 路径，/new 固定开在 hal #BBB/Agent-Bridge ✅ 2026-11-10
	- [ ] [下一步](https://bridge.example/control/sessions/<会话 ID>?item=jn-00e1610d-1110-next)：按共识写自进化设计文档 #BBB/Agent-Bridge
	- [ ] [等你](https://bridge.example/control/sessions/<会话 ID>?item=jn-00e1610d-1110-human)：确认设计后再动代码 #BBB/Agent-Bridge
	- [ ] [被打断](https://bridge.example/control/sessions/<会话 ID>?item=jn-91d2…-1110-interrupted)：部署重启时停下，没有继续 #BBB/Agent-Bridge
- Live2D AI音乐电台
	- [x] 查明直播自停根因：推流端断开 #BBB/Live2D-AI音乐电台 ✅ 2026-11-10
- 自动任务
	- 共 14 个任务跑了 31 次：成功 29，失败 1，静默 1；crypto 巡检 03:00 失败（一句话原因）
%%agent-journal:end%%
```

- 做完的写成已勾选的任务 `- [x] … ✅ <日期>`，带项目 tag：Tasks 插件和项目卡把它算作这天完成的事，成为项目的进展流水。
- 要人介入、或 agent 还有下一步的写成 `- [ ]`，带项目 tag。开头的状态词（下一步、等你、被打断……）就是链接，点开到 Control Center 里那个会话或自动任务；链接的 `?item=` 是条目 ID（由会话 ID、日期和种类派生，稳定），笔记里不另写 ID，Control Center 不理会这个参数。会出现在项目卡的「任务」（`TaskListByTag`）和 `任务.md` 里，没处理就一直挂着。
- 被自动关闭的条目，到它所在那天的日记里勾上，并加 `✅ <日期>`。
- 记忆候选不写进笔记（§7）；自动任务那组里只写一行「写入 N 条，M 条等你审核」，链到 Control Center 的审核面板。
- 链接指向 Control Center 的会话页（`/control/sessions/<id>`）或自动任务页（`/control/automations/<id>`），可以马上接着做。Control Center 的地址由任务配置给出。
- 重新生成时整段替换，但先读一遍旧段落，按链接里的条目 ID 保留人打的勾。人在这一段里改的其他文字会被覆盖；要长期留的话写到段落外面。

**项目怎么对应：** 先取会话的作用域（`group_key`），再由作用域对应到 LifeOS 项目 tag。计划用作用域 `scope.md` 里已有的 `para_note` 字段指向项目卡，脚本读项目卡得到 tag；原型阶段先用一份对照表。很多项目起初是在 Agent Bridge 里聊出来的，之后才单独立项，所以早期会话挂在 `#BBB/Agent-Bridge` 下是正常的。对不上的会话归到「其他」：不是每件事都有项目卡，不提醒。

**写入方式：** 直接写 HAL 上的笔记库（Syncthing 同步到各端）。先写临时文件再改名替换；写之前比对 mtime，读完到写入之间文件被改过就重读重做一次，避免覆盖人刚在手机上的修改。

## 9. 早上的简报（下一阶段）

07:00 把昨天的结果发到笔记房间。和本阶段相互独立，日记跑稳之后再做。

## 10. 原型和迭代

先不改 Control Plane：在 HAL 上用脚本只读数据库，抽出某天的会话，按 §3–§8 的规则用 TokensAPI `deepseek-v4-flash` 整理。分两部分：审核模型读对话写摘要和归档决定；渲染是普通脚本，把结果写进日记。记忆归档只演练：列出要写的作用域、新建的作用域和决定，不真写。

跑过的数据和每轮改的规则：

| 轮次 | 数据 | 发现 | 改了什么 |
| --- | --- | --- | --- |
| v1–v2 | 11-11 | 并发撞 429；长会话预算在思考里耗尽 | 改为逐个调用，预算加大 |
| v3 | 11-10 | 完成项太长（平均 62 字，最长 170），塞了 PID、哈希、路径；会话归错项目 | 作用域改取 `group_key`；作用域重构（根目录和家目录只精确匹配，`scope create` 同时绑仓库和目录） |
| v4 | 11-10 | 记忆写得太宽（只对一个工具成立的写成通用规则）；架构选择被当成记忆；新作用域用拼音、标题写成当天的事 | 完成项 40 字以内、只留一个数字（平均降到 29 字）；记忆写明「在 X 里」；架构、模块拆分、仓库选择 skip；起名规则；冲突交人审 |
| v4 | 11-09 | 模型漏掉一条候选；配色这类界面取舍被当成记忆；人说明的个人处境被 skip | 漏掉的列为待定；配色样式文案 skip；个人持续处境记为 `fact` |

已知的限制，之后按实际情况调：

- 同样的输入重跑，个别候选的决定会变；界面细节偶尔还会漏进记忆。
- 别的程序经 Bridge 发起的会话（电台观众对话）还分不出来（§3）。
- 项目单独立项后，旧目录下的会话还归在原作用域（例如从 new-api 独立出来的 BenchFront），要人用 `scope_bind` 调整。

格式和判断规则已定，下一步落成 §11 的模块和自动任务，真写记忆从那时开始。

## 11. 接口

Control Plane（`apps/control-plane/src/journal.ts` 新模块，表在同一个 SQLite 里）：

- `POST /api/v1/journal/runs` `{ date?: "YYYY-MM-DD", tz? }`：整理这一天（默认昨天，时区默认 Control Plane 的 `TZ`），返回各会话的状态和摘要（带作用域）、自动任务汇总、记忆候选和归档决定（`action` 为 `project` / `global` / `skip` / `human`；要先建作用域的带 `create`）、未关闭的条目和这次自动关闭的条目。同一天重跑只重读变了的会话（§4）。一天要几分钟：25 秒内没算完就回 `202 {state: "running"}`，调用方隔一会儿再发同样的请求，接上同一次运行。
- `GET /api/v1/journal/items?open=1&scope=&date=`：查条目。
- `POST /api/v1/journal/items/:id/close`：人勾掉了。
- 记忆归档不另开接口：日志任务用 memory 的 `write`、`scope`（`create: true`）写入，`_` 作用域照常经过自动审核。
- 权限：读接口对所有 token 开放；`runs` 和 `close` 要写权限。日志任务用自己的 `AGENT_TOKENS` token。
- 以后：`/mcp/bridge` 加只读工具 `journal`，agent 能问「这个项目最近干了什么、还有什么没关」。

agent-skills：`automations/daily-journal/`（任务定义 + 脚本），调度 `0 7 * * *`（简报阶段再加 `deliver`）。

## 12. 交付和验收

一次交付：Control Plane `journal` 模块（API、MCP 工具、测试）+ agent-skills 的任务和脚本，一起上线。

验收：

1. 重启 HAL Bridge 打断一个 turn，第二天日记里有 ⏸ 条目；续上之后下一次运行自动勾掉。
2. 主动 `!stop` 的会话不出现在「被打断」里。
3. 结尾在问人的会话出现在 🙋 里。
4. 中途杀掉任务再重跑，日记和账本都没有重复条目。
5. 人在手机上勾掉一条，下一次运行后账本里关闭，重新生成段落时勾选还在。
6. 人在对话里纠正过做法，第二天中央记忆的项目作用域里有这条，`derived_from` 指回原消息；同一槽位被人改过时放弃并提示；没有作用域的目录建出 provisional 作用域并立刻分组。
7. 项目卡的「任务」能显示 agent 段落里带 tag 的条目（已在 11-10 的日记里确认）。
